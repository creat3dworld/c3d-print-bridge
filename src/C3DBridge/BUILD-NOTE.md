# ADDENDUM — projection fix (Nov 1, 2026, after first install)

First install (build 0 errors, restart clean, config/key hashes unchanged) left the U1 panels unchanged: Thermals "Not reported", Files/Job history "Not available". Cause found in code, not guessed: DashboardClient.PushStatusAsync re-projects PrinterStatus into an anonymous object listing only a subset of fields — the Worker overlays (nozzle diameters, last-parse fields, and the new thermals / printer files / job history) were silently dropped before sending, so the dashboard could never receive them. This also explains why the bridge-reads nozzle-size / last-file-tool display was never proven live. Fix: the projection now carries every field the dashboard reads (nozzle_diameters, declared_file_tool, declared_tool_sequence, file_profile, file_nozzle_mm, thermals, printer_files, job_history), with null preserved for never-fetched files/history so the dashboard keeps rendering "Not available" rather than "None" in that case. Separately: the bridge log's "dashboard rejected the bridge API key" warnings ran 03:42–07:23 pre-restart and stopped at the restart; heartbeat (07:30:58) and snapshots (07:31) are fresh after it, so authenticated pushes are flowing now and the key warnings are not the panels' cause. No key or dashboard setting was changed for this fix.

# ADDENDUM — instant-push / instant-check speed fix (Nov 3, 2026, code only, NOT compiled, NOT installed)

Marlena's rule: when Send/print is hit, the file push must start immediately (no poll-tick wait) and status must show pushing → started near-instantly. Built on top of the Bambu plate fix above; one later install carries BOTH.
- Worker.cs: FarmPoller.PollAsync moved OUT of the job-poll gate (default 30 s) to EVERY loop tick (~5 s + work time), so a Send/Start dispatch is picked up within ~one tick. Same rejected-key guard as the gate (a rejected key still pauses farm polling). Side effect, documented not hidden: farm starts no longer wait on the bridge/jobs mirror poll succeeding, and farm controls (lights/home/power intents) are also picked up within ~one tick.
- Worker.cs + FarmPoller.cs: new FarmPoller.HasUnconfirmedStart() (true while a bridge-started farm job has not yet been seen printing). While true, the Worker forces a fresh status poll + push on every loop tick instead of waiting for the status interval (default 30 s), so "printing" is confirmed within ~one tick of the printer actually starting. It goes false on printing confirmation (or job end), so normal cadence resumes on its own; the monitor's 2-minute no-start failure still bounds it.
- NOT changed: every start gate in TryStartFarmJobAsync (dispatch=start, queued/pending_bridge_confirmation, live idle, bed + AMS confirmed, live AMS contradiction check, file gates, sliced-for match, SHA-256 download, tool gate on known values only); the Bambu plate gate (.gcode.3mf passes for BambuAdapter only) and the plate parse skip; Bambu dispatch shape (FTPS /cache + project_file "/cache/" + fileName); single-starter rule; pick_checked_printer (dashboard side, untouched).
- Known limit, not hidden: the push itself still takes as long as download + FTPS upload + start command (seconds for a plate). The fix removes the wait BEFORE the push starts and the wait before "printing" is confirmed; it does not make the transfer itself instant.
- Intervals after this fix: loop tick 5 s; farm poll every tick (~5 s); status forced every tick while a farm start is unconfirmed, else StatusIntervalSeconds (default 30 s); bridge/jobs + slice + OCR + reconcile stay on JobPollIntervalSeconds (default 30 s). No new config knobs, no config change needed on the shop PC.
- INSTALL (owed): compile on the shop PC (no dotnet on the VM), push per the standing auto-push rule, install only via stop-then-start of scheduled task "C3D Print Bridge" with backup + config/key hash verification + check-in verification. Version constant NOT bumped (same precedent as above).

# ADDENDUM — curl-based FTPS uploader (Nov 4, 2026, code only, NOT compiled, NOT installed)
Diagnosis chain, all proven live Nov 3, 2026 (no guessing): X2D FTPS login succeeds; /cache was missing (created via MKD, test upload then succeeded); curl uploads of a tiny file AND a 90MB file succeeded to /cache; the bridge's built-in SslStream uploader still failed on the real 13MB file with the connection forcibly closed. Root cause: the built-in uploader opens a fresh data-channel TLS session and sends no PBSZ/PROT; Bambu printers on current firmware refuse that combination. Size, folder, and credentials are all ruled out.
- Printers/BambuAdapter.cs: new CurlFtps class (curl.exe, temp config file deleted afterwards, credentials never on the command line, returned reasons redacted, uploaded byte count verified against the file size). UploadFileAsync now uses CurlFtps first and falls back to ImplicitFtps only when curl.exe is absent. ImplicitFtps kept, unchanged, as that fallback. KNOWN LIMITS comment updated to match.
- INSTALL (owed): compile on the shop PC (no dotnet on the VM), push per the standing auto-push rule, install only via stop-then-start of scheduled task "C3D Print Bridge" with backup + config/key hash verification + check-in verification, in a safe window (no printer printing/paused). Live proof owed: the collar send to the X2D reaching printing (not dispatch alone).
